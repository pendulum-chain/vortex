# Security Specification Review — 2026-07-24

## Status

- **Review type:** Spec-first security review with targeted implementation cross-checks
- **Repository baseline:** `1ff8299b1` (`staging`)
- **Review branch:** `codex/security-spec-review-2026-07-24`
- **Scope:** `docs/security-spec/` and implementation evidence needed to evaluate whether the specification itself is sound
- **Purpose:** Proof-reading and follow-up review by another AI agent or human reviewer

## Executive Summary

The current security specification should not yet be treated as a reliable source of truth. It contains:

- requirements that are unsafe even when implemented exactly as written;
- direct contradictions between modules;
- implementation descriptions that are materially stale;
- security guarantees that are impossible to enforce as formulated; and
- important trust boundaries that are not specified at all.

This review deliberately distinguishes:

1. **Spec defect:** the requirement is wrong, contradictory, misleading, incomplete, or unsafe.
2. **Conformance defect:** the requirement is sound, but the implementation does not satisfy it.

The findings below focus on the first category. Implementation references are included only where they demonstrate the practical consequence of a spec defect or prove that a supposedly current implementation description is obsolete.

The most urgent changes are:

1. specify webhook ownership, SSRF protection, and replay protection;
2. remove the raw-input-as-USD fallback from discount calculations;
3. replace the obsolete fee-integrity document;
4. correct authentication downgrade and upstream-outage semantics;
5. define aggregate subsidy exposure limits; and
6. separate normative requirements from conformance results and historical findings.

## Severity Guide

| Severity | Meaning |
|---|---|
| Critical | Following the specification can directly create unauthorized access, fund loss, or a materially false audit conclusion. |
| High | The specification permits significant security or financial failure, or contains contradictions that prevent a coherent implementation. |
| Medium | The specification weakens defense in depth, creates avoidable operational/security risk, or is materially misleading. |
| Low | Primarily clarity, maintainability, or auditability risk with limited direct security impact. |

## Findings

### SPEC-001 — Webhook authorization, SSRF, and replay protection are unspecified

- **Severity:** Critical
- **Type:** Missing security boundary

The server-side signing specification describes RSA-PSS mechanics but does not define:

- who may register a webhook for a quote or session;
- how a webhook subscription is bound to a partner or user principal;
- who may delete a webhook;
- which callback destinations are permitted;
- how redirects and DNS resolution are handled;
- what exact bytes are signed;
- how consumers reject replayed events; or
- how retries remain idempotent.

**Spec evidence**

- `docs/security-spec/02-signing-keys/server-side-signing.md:18-20`
- `docs/security-spec/00-system-overview/architecture.md:58`

**Implementation consequence**

- Registration checks only that a quote exists; it does not verify that the authenticated API key owns the quote: `apps/api/src/api/services/webhook/webhook.service.ts:57-75`.
- The webhook model has no partner, user, or API-key owner field: `apps/api/src/models/webhook.model.ts:5-14`.
- Deletion is by webhook UUID without an ownership predicate.
- Any HTTPS URL is accepted without private-address, link-local, DNS-rebinding, or redirect checks: `apps/api/src/api/services/webhook/webhook.service.ts:14-27`.
- `X-Vortex-Timestamp` is sent next to the signature but is not included in the signed bytes: `apps/api/src/api/services/webhook/webhook-delivery.service.ts:23-42`.

An authenticated but unrelated API client can therefore attempt to subscribe to another client's quote events. The delivery mechanism also creates a blind server-side request surface. Finally, a consumer that follows the implementation comment and checks only `X-Vortex-Timestamp` can be fooled by replaying a valid body/signature with a replaced current timestamp.

**Recommended normative replacement**

The spec should require all of the following:

1. Every webhook row has a canonical owner principal.
2. Registration for a quote or session requires proof that the principal owns that resource.
3. Read/update/delete operations are owner-scoped and return uniform not-found responses for foreign IDs.
4. Callback URLs are parsed canonically and restricted to HTTPS.
5. DNS is resolved before every delivery; all resolved addresses must reject loopback, private, link-local, multicast, and other non-public ranges.
6. Redirects are either disabled or revalidated at every hop.
7. The signed message is unambiguous, for example `version + "." + timestamp + "." + eventId + "." + body`.
8. Consumers reject timestamps outside a bounded window and deduplicate `eventId`.
9. Retries reuse the same `eventId` so retry and replay semantics are distinguishable.

### SPEC-002 — Discount fallback permits the same currency-unit error the spec says caused a 5× over-subsidy

- **Severity:** Critical
- **Type:** Unsafe requirement and direct contradiction

The discount overview says a fiat-pegged stablecoin whose price lookup fails may fall back first to a bridged USDC amount and then to the raw input amount:

- `docs/security-spec/03-ramp-engine/discount-mechanism.md:14`

Invariant 13 in the same document says off-ramp expected output must always be computed from a USD-denominated input. It explicitly documents the historical failure where 1,000 BRLA was treated as 1,000 USD, inflating the subsidy exposure by roughly the BRL/USD rate:

- `docs/security-spec/03-ramp-engine/discount-mechanism.md:42`

The implementation follows the unsafe wording:

- `apps/api/src/api/services/quote/engines/discount/helpers.ts:107-138`

When no bridged USDC amount is available, `usdFallbackFromContext` returns `ctx.request.inputAmount` without conversion.

**Why the formulation is invalid**

A monetary amount without its currency unit is not a safe fallback for an amount in another currency. Availability concerns cannot justify substituting BRLA, EURC, or an arbitrary token amount as USD.

**Recommended normative replacement**

For non-USD inputs, the discount engine must obtain one of:

1. a valid and bounded conversion to USD; or
2. an independently computed USD-denominated route amount whose provenance and timestamp are part of quote state.

If neither exists, quote creation must fail closed. Raw input amounts must never cross currency units as a fallback.

### SPEC-003 — `fee-integrity.md` describes an obsolete fee architecture

- **Severity:** Critical
- **Type:** Stale source-of-truth document

The document claims two parallel fee systems exist:

- token-config functions determine actual deductions; and
- database fees are stored/displayed but do not affect user output.

See:

- `docs/security-spec/03-ramp-engine/fee-integrity.md:7-15`
- `docs/security-spec/03-ramp-engine/fee-integrity.md:42`
- `docs/security-spec/03-ramp-engine/fee-integrity.md:69-72`

The specifically named deduction functions no longer exist in the current repository. The current quote pipeline uses `calculateFeeComponents` and `calculatePreNablaDeductibleFees`; fee summary construction describes itself as the single source of truth:

- `apps/api/src/api/services/quote/engines/initialize/index.ts:42-73`
- `apps/api/src/api/services/quote/engines/nabla-swap/index.ts:35-39`
- `apps/api/src/api/services/quote/engines/fee/index.ts:50-68`
- `apps/api/src/api/services/quote/engines/fee/index.ts:76-84`

The rounding description is also incorrect. It describes Big.js rounding mode `0` as half-up and mode `1` as half-down:

- `docs/security-spec/03-ramp-engine/fee-integrity.md:51`
- `docs/security-spec/03-ramp-engine/fee-integrity.md:78`

Big.js defines these as round-down and round-half-up, respectively.

**Impact**

An auditor following this document will:

- report obsolete critical failures;
- inspect removed functions;
- misunderstand current deduction timing;
- potentially miss present-day discrepancies between quote snapshots, on-chain distribution, and provider charges.

**Recommended normative replacement**

Rewrite the module around the current pipeline and define, for each corridor:

1. canonical fee inputs and their configuration source;
2. fee currency and conversion source;
3. the immutable quote-time fee snapshot;
4. exact deduction point;
5. exact distribution point;
6. rounding direction at every decimal/raw conversion;
7. equality or reconciliation requirements between displayed, deducted, distributed, and provider-charged fees; and
8. legacy-quote behavior after configuration changes.

### SPEC-004 — Optional authentication explicitly permits credential downgrade

- **Severity:** Medium (downgraded from High after verification, 2026-07-24)
- **Type:** Unsafe authentication semantics

> **Verification note (2026-07-24):** All factual claims confirmed, but the impact is
> bounded: the token-fragment truncation format is explicitly sanctioned by the spec
> itself (invariant 6), and the anonymous-claim design (quote-lifecycle invariant 17,
> provider identity re-derived from the claimer's KYC) means a silent downgrade cannot
> grant access to another principal's resources. The downgrade-semantics principle and
> the recommended 401/503 taxonomy stand.

The Supabase specification requires `optionalAuth` to ignore an invalid or expired credential and continue anonymously:

- `docs/security-spec/01-auth/supabase-otp.md:24`

The implementation also continues anonymously on verification exceptions and logs token fragments:

- `apps/api/src/api/middlewares/supabaseAuth.ts:51-77`

**Why this is unsafe**

There is an important difference between:

- a caller that deliberately sends no credential; and
- a caller that attempts authenticated behavior with an invalid credential.

Silently downgrading the latter can create an anonymous quote when the client believed it created a user-owned quote. This is a confused-deputy and ownership-consistency risk.

**Recommended normative replacement**

- Missing header on an explicitly anonymous-eligible endpoint: continue anonymously.
- Present but malformed/invalid/expired credential: return `401`.
- Verification infrastructure failure: deny the operation but return `503`, not `401`.
- Never log bearer-token fragments; log a non-secret request ID and stable error category.

### SPEC-005 — Supabase verification is incorrectly tied to the service-role key

- **Severity:** High
- **Type:** Incorrect security property

The spec says JWT verification must use the Supabase service-role key and treats client-side/anon-key verification as insufficient:

- `docs/security-spec/01-auth/supabase-otp.md:21`

This formulation confuses a privileged API credential with token authenticity. The security properties that matter are:

- trusted issuer/project;
- correct signature or authoritative server-side introspection;
- expected audience;
- expiry and not-before checks;
- canonical subject extraction; and
- revocation behavior where required.

Using a service-role key does not inherently strengthen those checks and increases the blast radius of the verification component.

The current code uses the service-role client:

- `apps/api/src/config/supabase.ts:4-9`
- `apps/api/src/api/services/auth/supabase.service.ts:159-174`

**Recommended normative replacement**

Permit either:

1. authoritative Supabase Auth validation over a server-controlled channel; or
2. local JWT verification against pinned project metadata/JWKS with issuer, audience, expiry, and algorithm restrictions.

The service-role key should be required only for operations that actually need service-role privileges.

### SPEC-006 — Access-token outage semantics contradict refresh-token outage semantics

- **Severity:** High
- **Type:** Internal inconsistency

For normal access-token verification, the spec requires every error, including a network error, to return `401`:

- `docs/security-spec/01-auth/supabase-otp.md:25`

For refresh, the spec correctly requires transient upstream failures to return `503` so an outage cannot masquerade as invalid credentials:

- `docs/security-spec/01-auth/supabase-otp.md:29`

The same distinction should apply to access-token verification. A `401` means the credential is invalid and may trigger logout/refresh behavior; it is not the correct status for an authentication-provider outage.

**Recommended normative replacement**

Define a stable error taxonomy:

- missing/invalid/expired/revoked credential: `401`;
- valid credential but insufficient authority: `403`;
- authentication provider unavailable or indeterminate: `503`, with no anonymous fallback.

### SPEC-007 — Architecture-wide authentication rules contradict the public quote design

- **Severity:** High
- **Type:** Direct contradiction

The architecture spec says every client-facing endpoint must enforce authentication and that no quote mutation endpoint may be unauthenticated:

- `docs/security-spec/00-system-overview/architecture.md:62`

The quote and API-surface specs explicitly make quote creation anonymous-eligible:

- `docs/security-spec/03-ramp-engine/quote-lifecycle.md:74`
- `docs/security-spec/07-operations/api-surface.md:52`

The architecture also says trust boundaries must be enforced in middleware and never in controllers:

- `docs/security-spec/00-system-overview/architecture.md:63`

That is too absolute. Authentication belongs at the HTTP boundary, but resource authorization often needs loaded domain state and must also be enforced in service-layer invariants.

**Recommended normative replacement**

Provide an endpoint matrix defining:

- whether anonymous access is allowed;
- accepted credential types;
- effective principal;
- resource-ownership rule;
- whether the resource becomes anonymous, user-owned, or partner-owned; and
- service-layer defense-in-depth checks.

Split the requirement into authentication at the boundary and authorization at every operation that touches an owned resource.

### SPEC-008 — Subsidy limits do not bound aggregate ramp or platform exposure

- **Severity:** High
- **Type:** Incomplete financial invariant

The specification permits independently capped components:

- swap discrepancy subsidy;
- discount subsidy; and
- final-settlement subsidy.

See:

- `docs/security-spec/03-ramp-engine/discount-mechanism.md:38`
- `docs/security-spec/06-cross-chain/fund-routing.md:39-45`

The phase-flow spec simultaneously says every subsidization handler must enforce a maximum USD-equivalent cap:

- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:181`

There is no normative bound for:

- total subsidy across all phases of a ramp;
- total subsidy per user, API key, partner, or corridor;
- total funding-account outflow per time window; or
- concurrent ramps exhausting a pooled funding account.

Two separately allowed 5% components can already permit approximately 10% before final settlement is considered.

**Recommended normative replacement**

Define nested limits:

1. per-component;
2. per-ramp aggregate;
3. per-principal and per-partner rolling window;
4. per-corridor rolling window; and
5. global funding-account circuit breaker.

All checks should use a canonical USD valuation and an atomic reservation/consumption model so concurrent ramps cannot each observe the same remaining budget.

### SPEC-009 — `maxSubsidy = 0` means uncapped

- **Severity:** High
- **Type:** Dangerous configuration semantics

The discount spec describes `maxSubsidy` as a fractional cap but applies it only when the value is greater than zero:

- `docs/security-spec/03-ramp-engine/discount-mechanism.md:30`

The implementation returns the full shortfall when the value is zero:

- `apps/api/src/api/services/quote/engines/discount/helpers.ts:227-242`

For a field named "maximum subsidy," zero naturally means no subsidy, not unlimited subsidy. This is a configuration footgun.

**Recommended normative replacement**

- `0` means subsidy disabled.
- A positive fraction in `(0, 1]` means capped.
- If uncapped behavior is ever permitted, represent it explicitly with a nullable value or enum and restrict it to reviewed configuration paths.

### SPEC-010 — A 90% arrival threshold is not proof of final bridge delivery

- **Severity:** High
- **Type:** Unsafe settlement algorithm

The final-settlement subsidy invariant allows the handler to consider bridge delivery sufficiently established when at least 90% of the expected amount has arrived:

- `docs/security-spec/06-cross-chain/fund-routing.md:45`

The platform may then top up the remaining shortfall. If the remaining bridge output arrives later, the ephemeral becomes overfunded by up to roughly the tolerated gap.

This improves on returning after any non-zero dust, but it remains a heuristic and not a finality guarantee.

**Recommended normative replacement**

Subsidization should require:

1. authoritative terminal bridge status;
2. finalized destination-chain balance observation;
3. a defined settlement/reconciliation delay when the provider can deliver in parts; and
4. post-settlement reconciliation or recovery for late delivery.

If the bridge cannot provide a final delivered amount, the accepted exposure and recovery procedure must be explicit.

### SPEC-011 — Cross-chain finality requirements contradict the Hydration rule

- **Severity:** High
- **Type:** Direct contradiction

The architecture and ramp-flow specs require finalization before advancing:

- `docs/security-spec/00-system-overview/architecture.md:69`
- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:184`

The XCM spec requires Hydration→AssetHub to proceed without finalization and acknowledges reorganization risk:

- `docs/security-spec/06-cross-chain/xcm-transfers.md:31`

An implementation cannot satisfy both requirements.

**Recommended normative replacement**

Define a general finality objective and corridor-specific evidence:

- normal route: source finalization plus destination receipt;
- exceptional route where source finalization APIs are unavailable: destination receipt after an explicit confirmation depth and/or later source-finality reconciliation;
- failure/reorg: compensating transition and operator alert.

An accepted exception must include equivalent detection and recovery controls, not merely document that reorganization is possible.

### SPEC-012 — Fee-ordering invariants contradict documented corridor flows

- **Severity:** High
- **Type:** Direct contradiction

The phase-flow security invariant says fee distribution must happen after all user-facing phases complete:

- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:185`

The fee-integrity document says Base BRL off-ramp fee distribution occurs before Nabla swap:

- `docs/security-spec/03-ramp-engine/fee-integrity.md:35-38`

The latter may be the correct corridor-specific financial design, but the global invariant makes it a violation.

**Recommended normative replacement**

Do not prescribe a universal chronological position. Require instead that:

1. fee deduction/distribution order is defined per corridor;
2. the order matches the currency in which fees were quoted;
3. failed ramps have a refund/recovery rule for already-distributed fees; and
4. the user-visible net amount remains consistent with the quote.

### SPEC-013 — Required transaction guards are explicitly allowed to fail open

- **Severity:** High
- **Type:** Unsafe exception language

The ramp-flow spec says destination transfers must detect nonce gaps, then states that RPC or decode failures may fall through to normal broadcast:

- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:189`

It also requires presigned payouts to be balance-checked, then allows unparseable or non-transfer payloads to fall through to broadcast:

- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:191`

These exceptions negate the preceding MUST requirements exactly when the system cannot establish transaction safety.

**Recommended normative replacement**

- Failure to parse a server-generated/signed transaction is unrecoverable corruption and must stop.
- RPC inability to perform a required preflight is a recoverable service failure and must stop the attempt.
- Only checks explicitly classified as non-security observability may be best-effort.
- A fallback broadcast must never be the response to inability to validate transaction content, nonce, chain, signer, or funding.

### SPEC-014 — Ephemeral-key localStorage requirements are impossible and over-retentive

- **Severity:** High
- **Type:** Impossible guarantee and unsafe retention rule

The spec says plaintext keys in localStorage must not be accessible to third-party scripts:

- `docs/security-spec/02-signing-keys/ephemeral-accounts.md:30`

Any JavaScript executing in the same origin can access localStorage. This cannot be guaranteed by the storage design.

The spec also mandates preserving keys across:

- ramp completion;
- failures;
- cancellation;
- starting another ramp; and
- logout.

See:

- `docs/security-spec/02-signing-keys/ephemeral-accounts.md:32`

The threat table acknowledges indefinite accumulation and XSS exposure:

- `docs/security-spec/02-signing-keys/ephemeral-accounts.md:46`

**Recommended normative replacement**

Define:

1. the exact recovery threat being addressed;
2. minimum required retention period;
3. automatic deletion after terminal settlement plus a bounded recovery window;
4. explicit user export/recovery workflow;
5. cleanup on shared-device logout where appropriate;
6. prohibition on claiming that localStorage isolates data from same-origin scripts; and
7. an XSS/CSP dependency statement.

For the SDK, plaintext filesystem storage should default off or use restrictive creation permissions and an explicit deletion lifecycle.

### SPEC-015 — Ephemeral freshness is both inconsistent and availability-hostile

- **Severity:** Medium
- **Type:** Contradictory requirement and excessive dependency scope

The signing-key spec requires zero nonce, zero balance, or nonexistence as appropriate on every supported chain:

- `docs/security-spec/02-signing-keys/ephemeral-accounts.md:29`

Its checklist describes EVM freshness as nonce-only:

- `docs/security-spec/02-signing-keys/ephemeral-accounts.md:61`

An EVM account can have nonce zero while already holding native or token balances. The checklist therefore does not prove the stated invariant.

The requirement also makes every registration depend on every supported same-type chain, including chains unrelated to the route. An outage of an unrelated RPC can block all new ramps.

**Recommended normative replacement**

- Define freshness per chain and per signing model.
- Validate every chain the constructed ramp can actually use, including fallback/recovery phases.
- Require route construction tests to keep this set synchronized with handlers.
- Treat future chains as unavailable until their freshness checker is registered.
- Avoid making an unrelated chain's RPC a universal registration dependency.

### SPEC-016 — Cleanup authority contradicts Stellar 2-of-2 signing

- **Severity:** Low (downgraded from High after verification, 2026-07-24)
- **Type:** Misleading wording, not a direct contradiction

> **Verification note (2026-07-24):** The wording tension is real, but "direct
> contradiction" is overstated: the spec's own architecture section describes a
> presigned `stellarCleanup` XDR, and every implemented cleanup handler uses the
> presign-by-client + cosign/broadcast-by-server model, which is fully consistent with
> 2-of-2 signing. Moreover, no Stellar cleanup code exists in the current repository
> (Stellar anchors were removed in migration 028), and Stellar support is obsolete and
> slated for removal, making this finding moot.

The server-side signing spec says the funding key alone cannot move funds from a Stellar ephemeral:

- `docs/security-spec/02-signing-keys/server-side-signing.md:17`

The lifecycle spec says cleanup relies on the server cosigner because the client key may be unavailable:

- `docs/security-spec/03-ramp-engine/ephemeral-accounts.md:41`

A signer with weight one cannot independently satisfy a threshold of two.

**Recommended normative replacement**

Specify the real authorization chain:

- the client signs a bounded cleanup transaction before the ramp starts;
- the server validates and stores it;
- the server adds its cosignature only when cleanup conditions hold; and
- sequence/time bounds, destination, assets, and operation count are validated.

If server-only recovery is desired, it requires a different threshold/recovery design and an explicit threat analysis.

### SPEC-017 — Admin authentication is intentionally identity-less

- **Severity:** Medium (downgraded from High after verification, 2026-07-24)
- **Type:** Design gap documented as an invariant

> **Verification note (2026-07-24):** Invariant 7 is an implementation-consistency rule
> for the current shared-secret model (do not fabricate a `req.adminUser` from a
> credential that identifies no one), not an affirmative counter-security mandate — the
> spec itself candidly flags the single-static-secret design as a limitation. The
> substantive critique (no attribution, revocation, MFA, or non-repudiation) and the
> recommended replacement stand.

The admin specification requires that no admin identity be attached to requests:

- `docs/security-spec/01-auth/admin-auth.md:23`

For a financial platform, a single shared static secret prevents:

- per-operator attribution;
- selective revocation;
- individual MFA;
- role separation;
- approval workflows; and
- reliable non-repudiation.

The spec also says admin access must not grant access to user funds:

- `docs/security-spec/01-auth/admin-auth.md:20`

That understates the actual indirect blast radius. Admin-controlled partner keys, pricing, discounts, roles, and profile assignments can materially change authorization and platform-funded payments.

**Recommended normative replacement**

Require individual admin identities, MFA, role-based authorization, immutable audit events, and least privilege. If `ADMIN_SECRET` remains temporarily, describe it as a high-blast-radius bootstrap/emergency credential and prohibit routine use.

### SPEC-018 — API-key verification canonizes an avoidable global authentication DoS

- **Severity:** High
- **Type:** Unsafe architecture requirement

All secret keys share the same eight-character prefix, so verification performs bcrypt comparisons against all active keys in the environment:

- `docs/security-spec/01-auth/api-keys.md:41`

The spec attempts to control this with a per-user active-key cap:

- `docs/security-spec/01-auth/api-keys.md:51`

A per-user cap does not bound:

- the number of users;
- admin-created partner keys;
- the total bcrypt work per authentication attempt; or
- aggregate attacker request volume.

**Recommended normative replacement**

Use a format with a random, non-secret key identifier and a high-entropy secret. Look up exactly one record by identifier, then compare a keyed HMAC or cryptographic digest in constant time. Slow password hashing is not necessary for uniformly random 190-bit secrets and increases online denial-of-service exposure.

The spec should also stop claiming that regex format validation prevents injection; parameterized database access is the relevant injection control.

### SPEC-019 — Recipient invitation retention claims contradict the actual lifecycle

- **Severity:** High
- **Type:** Contradictory and incomplete bearer-token lifecycle

The spec intentionally stores raw invite bearer tokens so senders can re-copy links:

- `docs/security-spec/03-ramp-engine/recipient-transfers.md:28-39`

It claims expired tokens are cleared, but clearing is triggered by acceptance or sender listing. An expired row that is never revisited can retain its raw token indefinitely.

It also says expired invites remain visible until archived and later says sender listing excludes expired rows:

- `docs/security-spec/03-ramp-engine/recipient-transfers.md:35-38`
- `docs/security-spec/03-ramp-engine/recipient-transfers.md:43-48`

The spec acknowledges there is no revocation endpoint:

- `docs/security-spec/03-ramp-engine/recipient-transfers.md:57-61`

**Recommended normative replacement**

- Prefer storing only a hash and issuing a replacement token when a sender requests a new link.
- If raw-token retention remains, encrypt it with a dedicated key and delete it via a scheduled expiry worker independent of reads.
- Add an explicit revocation endpoint and immediate raw-token deletion.
- Define consistent sender-list visibility separately from token redeemability.

### SPEC-020 — Recipient transfer authorization is still explicitly undefined

- **Severity:** High
- **Type:** Draft functionality presented inside an authoritative security module

The module labels ramp registration versus the recipient model as:

> PRESSING, TO BE DEFINED

See:

- `docs/security-spec/03-ramp-engine/recipient-transfers.md:155-184`

The existing eligibility endpoint is described as UX rather than a security boundary, and the registration API lacks a second principal. This means the document does not yet define how sender authorization, recipient identity, payout instrument ownership, and ramp settlement bind together.

**Recommended normative replacement**

Mark this part of the module as draft/non-authoritative until the model defines:

1. sender principal;
2. recipient relationship ID;
3. recipient entity and provider identity;
4. verified payout instrument;
5. corridor-specific eligibility;
6. registration-time atomic authorization;
7. post-registration immutability; and
8. revocation/block behavior for pending ramps.

### SPEC-021 — TokenRelayer ownership terminology is stale

- **Severity:** Medium
- **Type:** Incorrect invariant

The spec says only the deployer may withdraw tokens:

- `docs/security-spec/04-smart-contracts/token-relayer.md:33`

The contract uses OpenZeppelin `Ownable`, whose ownership can be transferred. Withdrawal is restricted to the current owner:

- `contracts/relayer/contracts/TokenRelayer.sol:196-200`

**Recommended normative replacement**

State that only the current contract owner may withdraw, then specify:

- whether ownership transfer is allowed;
- expected owner type, preferably a multisig/timelock;
- ownership-transfer monitoring; and
- emergency withdrawal policy.

### SPEC-022 — TokenRelayer amount binding is overstated

- **Severity:** High
- **Type:** False guarantee

The spec says `transferFrom` pulls exactly the signed value and that the same value is available to the forwarded call:

- `docs/security-spec/04-smart-contracts/token-relayer.md:35`

This is not generally guaranteed for fee-on-transfer, rebasing, callback-enabled, or otherwise non-standard tokens. In addition, the signed `value` and exact approval do not prove that arbitrary destination calldata consumes exactly that value for the intended action.

**Recommended normative replacement**

Either:

1. restrict supported tokens to an explicit allowlist with standard transfer semantics; or
2. measure the actual received balance delta and bind destination-call semantics to that value.

The spec must also define which destination methods/calldata shapes are permitted, or explicitly accept that the signed payload authorizes arbitrary calldata to the fixed destination.

### SPEC-023 — Quote “guaranteed minimum” language contradicts subsidy caps

- **Severity:** Medium (downgraded from High after verification, 2026-07-24)
- **Type:** Misleading wording (disclosed liveness exception)

> **Verification note (2026-07-24):** The cap-breach exception does not permit
> delivering less than the quoted output; it pauses the ramp for operator intervention.
> That is a disclosed liveness caveat, not a safety violation, so "contradictory
> financial promise" is overstated. The word "guaranteed" is still wrong and the
> recommended separation of concepts stands.

The quote lifecycle says the quoted output is the guaranteed minimum, then says a cap breach can leave the ramp waiting for operator intervention:

- `docs/security-spec/03-ramp-engine/quote-lifecycle.md:63`

A capped subsidy plus indefinite manual intervention is not a guaranteed delivery minimum.

**Recommended normative replacement**

Define separate concepts:

- quoted target output;
- hard minimum output;
- maximum platform subsidy;
- conditions under which execution pauses;
- cancellation/refund rights;
- operator SLA; and
- terminal reconciliation outcome.

Do not use "guaranteed" unless every terminal path specifies how that guarantee is fulfilled.

### SPEC-025 — Phase-transition validation is delegated to the code being constrained

- **Severity:** High
- **Type:** Tautological invariant

The state-machine spec says transitions must be validated, then says the handler is responsible for returning a valid next phase:

- `docs/security-spec/03-ramp-engine/state-machine.md:27`

The phase-flow spec similarly says each handler must return the expected next phase:

- `docs/security-spec/03-ramp-engine/ramp-phase-flows.md:180`

This does not create an independent security boundary. A handler bug can return an invalid transition and is also the component expected to decide that it is valid.

**Recommended normative replacement**

Define a machine-readable transition graph keyed by corridor/route version. The phase processor must independently reject any transition not present in that graph. Route construction and recovery transitions should be versioned and covered by exhaustive tests.

- **Severity:** High
- **Type:** Audit-process defect

The README says unchecked boxes are gaps:

In practice, checked boxes sometimes contain `FAIL`, `PARTIAL`, stale claims, or accepted vulnerabilities. Examples:

- evidence reference;
- reviewer;

### SPEC-027 — Normative requirements and audit history are mixed together

- **Severity:** High
- **Type:** Structural source-of-truth defect

The module files combine:

- intended invariants;
- current code behavior;
- line-number references;
- incident narratives;
- historical fixes;
- open findings;
- accepted risks; and
- dated verification claims.

As code changes, the descriptive and checklist sections become stale while still appearing authoritative. This is already visible in the fee, Supabase, route-auth, and TokenRelayer documents.

**Recommended document architecture**

1. **Normative specification**
   - stable requirement IDs;
   - no checkbox statuses;
   - no volatile source line numbers;
   - explicit assumptions and accepted-risk references.
2. **Conformance report**
   - generated or reviewed against one commit SHA;
   - evidence paths/tests;
   - pass/fail/partial status.
3. **Finding and risk register**
   - severity;
   - owner;
   - decision;
   - expiration/review date;
   - remediation link.
4. **Generated matrices**
   - endpoint/auth/ownership matrix;
   - corridor/phase/chain matrix;
   - signing-key/authority matrix;
   - fee/subsidy flow matrix.

## Cross-Cutting Recommendations

### 1. Define financial invariants in units

Every amount requirement should identify:

- currency/token;
- decimal/raw representation;
- price source and timestamp;
- rounding mode;
- maximum age;
- fallback behavior; and
- whether failure is recoverable or terminal.

No fallback may silently preserve a numeric value while changing its unit.

### 2. Separate safety from liveness

The spec frequently uses availability fallbacks inside security checks. Each requirement should say:

- whether failure to check blocks execution;
- whether the error is retryable;
- maximum retry duration;
- terminal state;
- manual recovery path; and
- whether any side effect may already have occurred.

Security validation of signer, chain, transaction content, nonce, ownership, or amount should fail closed.

### 3. Define aggregate platform-risk budgets

Per-operation caps are not sufficient for pooled funding accounts. The specification should define atomic aggregate budgets for subsidies, relayer gas, cleanup, bridge gas top-ups, and rebalancer operations.

### 4. Version routes and quotes

Long-lived or retryable state should carry a route/spec version. Otherwise a changed handler graph or fee/subsidy rule can reinterpret an older quote/ramp using new code.

### 5. Replace identity-less operational credentials

Admin, metrics, and high-impact operational actions should use individual identities, roles, MFA, and audit events. Shared secrets should be emergency-only and have explicit rotation and blast-radius documentation.
