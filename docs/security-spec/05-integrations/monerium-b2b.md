# Monerium B2B Whitelabel Onramp

## What This Does

The B2B zero-touch onramp (docs/architecture-monerium-b2b-onramp.md) gives each corporate client a Monerium IBAN linked to a per-client `VortexForwarder` contract. SEPA deposits mint EURe to the forwarder; a keeper later swaps and forwards USDC to the client's destination. This spec covers the backend integration built in `apps/api/src/api/services/monerium-b2b/`: the whitelabel API client, the attestor signature for address linking, the webhook receiver with durable inbox, the deposit processor, the managed-profile account mapping, and the onboarding automation. It is deliberately NOT part of the one-shot ramp state machine — accounts are persistent and repeatedly funded. Each account is owned by a Vortex **managed profile** (`monerium_accounts.vortex_profile_id`): the corporate is onboarded and KYB-approved on Monerium's side, then mapped into Vortex as a managed child with an approved `provider_customers`/`kyc_cases` mirror.

**Provider type:** on-ramp (EUR → USDC)
**Fiat currencies:** EUR
**Chains involved:** Ethereum (forwarder contracts, EURe/USDC)
**Modules:** `monerium-b2b/monerium-api.ts` (narrow adapter over the shared white-label client, [monerium.md](./monerium.md)), `monerium-b2b/attestor.ts`, `monerium-b2b/webhook.ts`, `monerium-b2b/deposit-processor.ts`, `monerium-b2b/account-provisioning.ts`, `monerium-b2b/refund-wallet.ts`, `monerium-b2b/onboarding.ts`, `monerium-b2b/registration.ts`, `controllers/monerium-b2b.controller.ts` (POST `/v1/monerium-b2b/webhook`; the manager routes `/v1/monerium-b2b/accounts` and `/registrations`), `controllers/admin/moneriumB2b.controller.ts` (POST `/v1/admin/monerium-b2b/accounts`, the registration list and withdrawal, the account status; ADMIN_SECRET); keeper: `monerium-b2b/chain.ts`, `monerium-b2b/mint-watcher.ts`, `monerium-b2b/conversion-executor.ts`, `monerium-b2b/dormancy.ts`, `workers/monerium-b2b.worker.ts`; monitoring: `monerium-b2b/monitoring.ts`
**API auth method:** OAuth client credentials through the shared `MoneriumApiService` (`MONERIUM_WHITELABEL_CLIENT_ID`/`MONERIUM_WHITELABEL_CLIENT_SECRET`) against `MONERIUM_API_URL` (defaults to sandbox `api.monerium.dev` while `SANDBOX_ENABLED`, `api.monerium.app` otherwise); inbound webhooks authenticated by HMAC-SHA256 (`MONERIUM_B2B_WEBHOOK_SECRET`)

## Security Invariants

0. **Dark by default and fail-fast on activation** — unless `MONERIUM_B2B_ENABLED` is exactly `true`, the public/admin B2B routes, raw webhook parser, keeper worker, and deposit-webhook registration are disabled. Existing generic webhook-outbox rows continue draining. Activation requires `FLOW_VARIANT=mykobo`, all whitelabel credentials, three keys, read RPC, webhook secret, and the trusted factory address; production also requires the private orderflow RPC. Missing configuration aborts startup rather than partially enabling the flow. Partner registrations (invariant 12) additionally need `MONERIUM_B2B_PARTNER_MANAGER_PROFILE_ID` and `MONERIUM_B2B_DEPLOYER_PRIVATE_KEY`, which startup accepts only together; without them the registration endpoint answers 403 and the keeper deploys nothing. The deployer key must differ from the attestor, guardian, keeper and float keys (it sends with implicit nonces, one EOA each), and the partner binding is compared lower-cased.
1. **Attestor key stays in env and out of logs** — `MONERIUM_B2B_ATTESTOR_PRIVATE_KEY` is read from the environment only, never persisted, never returned by an API response, and never included in log lines or error messages (the not-configured error names the variable, not the value).
2. **The attestor signature authorizes linking only** — the attestor signs exactly `keccak256(abi.encodePacked(block.chainid, forwarderAddress, hash))` (the chainid binding prevents cross-chain replay — review r1) where `hash` is `LINK_HASH_191`, the EIP-191 personal-message hash of `"I hereby declare that I am the address owner."` (the raw-keccak variant was removed after the G0 sandbox validation), or the optional non-zero `RECOVERY_HASH` reserved for a future distinct recovery message (kept `bytes32(0)`: Monerium's recovery flow validates the SAME ownership message as linking (registry T1), so the whitelisted `LINK_HASH_191` already covers issuer recovery — the signature proves only address ownership; the recovery payout target is Monerium's controlled process, paying exclusively to the customer's own verified bank account). `VortexForwarder.isValidSignature` accepts nothing else, so a leaked attestor key can link addresses but can never move funds or change forwarder config. The backend MUST never sign arbitrary hashes with this key.
3. **Signature format matches the contract check** — 65-byte `r ‖ s ‖ v` with `v ∈ {27, 28}` and low-s (the contract rejects malleable signatures). Enforced by construction (viem canonical signatures) and pinned by unit test `attestor.test.ts`.
4. **Webhook HMAC follows Monerium's current v1 protocol** — `webhook-signature` must contain exactly `v1,<base64>`. The HMAC-SHA256 input is `<webhook-id>.<webhook-timestamp>.<raw-body>` and the key is the decoded 24–64-byte payload of the configured `whsec_<base64>` secret. The raw bytes are captured by a route-scoped body-parser hook and compared with `crypto.timingSafeEqual`; malformed or unverified requests are rejected 401 before any database write.
5. **Durable persist before 200 (R06)** — every verified delivery is inserted into `monerium_webhook_events` before the 200 response is sent. Processing happens strictly after the response; a crash between insert and processing loses nothing because the inbox row survives.
6. **Delivery dedup is enforced by the database** — inserts use `ON CONFLICT DO NOTHING` on the unique `event_id`, populated from the signed `webhook-id` header, so retries of a delivery can never double-create or double-apply a deposit event.
7. **Deposit status transitions are forward-only** — provider states first: `pending → {minted, held, returned}`, `held → {minted, returned}`; then the keeper's settlement branch `minted → converting → forwarded` or the refund branch `{minted, converting} → recovering → {refunded, recovery_failed}` (`recovery_failed → recovering` is the operator's retry, `recovery_failed → refunded` the operator closing a refund completed by hand; only the admin endpoint and a processed redeem order ever request `refunded`). `forwarded`, `returned` and `refunded` are terminal. Out-of-order or replayed webhook events can never regress a deposit status: regressive transitions are logged and ignored, and a provider `processed` replay for a deposit already past the mint is a silent no-op. Guarded by `isForwardTransition` (unit-tested). Only the keeper (a confirmed `forward`), the refund path in `recovery.ts` (deadline marking, parking, a processed redeem order) and the admin endpoints move a deposit along the settlement and refund branches.
8. **Per-forwarder serialization via advisory lock** — all deposit writes for one forwarder happen inside a transaction holding `pg_advisory_xact_lock(hashtextextended('monerium-b2b:' || lower(forwarderAddress), 0))`, so concurrent processors (multiple API instances, webhook-triggered plus scheduled runs) apply events for an account strictly one at a time. This is the same serialization point the execution/attribution logic (R04) will use.
9. **Deposit identity and scope are verified** — authenticated payloads must pass the shared Monerium wire schema. Only EUR issue orders on the configured chain and the mapped account's Monerium profile are accepted; `meta.txHashes` is used only when it contains exactly one hash. `monerium_order_id` is unique and cannot move between accounts; the on-chain mint `(chain_id, tx_hash, log_index)` is a second partial-unique identity. Amounts are positive 18-decimal base-unit strings converted from provider decimals, never floats. An amount-only mint match is accepted only when exactly one same-account candidate exists. A late real order in a minted provider state reconciles its unique exact same-account unattributed mint by amount and transaction hash: a missing provider row adopts the synthetic row, while an existing provider row receives the chain identity and allocations atomically before the synthetic row is removed. Pending or terminal provider states never adopt a synthetic mint. Ambiguity is quarantined and alerted, never guessed. Malformed authenticated deliveries are terminally discarded so they cannot poison the inbox.
10. **Client credentials are env-only and requests are bounded** — all provider calls go through the shared white-label client ([monerium.md](./monerium.md)): credentials come from env (`MONERIUM_WHITELABEL_CLIENT_ID/SECRET`), every call carries an explicit timeout, HTTPS base URLs only, successful responses are validated against the consumed wire schemas, and upstream failures surface with redacted response bodies. The B2B adapter (`monerium-api.ts`) adds no transport of its own.
11. **No KYB submission path exists** — the whitelabel KYB submission mechanism is deliberately unbuilt (adr-0005 registry T3), so no identity-data submission code path exists in the B2B module or the shared client. Clients do not need one: they are onboarded and KYB-approved by Monerium, and the admin mapping imports that outcome as an approved `kyc_cases` row.
12. **Account mapping is admin-or-registration, atomic, and rooted in a trusted factory** — an account is created only by `POST /v1/admin/monerium-b2b/accounts` (ADMIN_SECRET) or by the keeper for a partner registration, and both go through the same `provisionMoneriumB2bAccount`. A registration (`POST /v1/monerium-b2b/accounts`, `registration.ts`) is accepted only from the manager bound to the white-label app by `MONERIUM_B2B_PARTNER_MANAGER_PROFILE_ID`, never with an admin impersonation token (403 `IMPERSONATION_NOT_ALLOWED`; [admin-impersonation.md](../01-auth/admin-impersonation.md) invariant 18), and only for a profile that app can read and Monerium has neither rejected nor closed (422 `MONERIUM_B2B_PROFILE_UNAVAILABLE`; a Monerium failure, timeout, rate limit or 403 is 503 `MONERIUM_B2B_PROVIDER_UNAVAILABLE`, never blamed on the partner's input). It is create-only per Monerium profile (unique row): an identical replay returns its state, any difference in destination, client reference or contact email (compared case-insensitively) is 409 `MONERIUM_B2B_DESTINATION_CONFLICT`, a profile that already has an account is 409, and a client conflict — the client reference already used with a different contact email, by a non-business or with another Monerium profile, the contact email used by another client, or another non-rejected registration with the same reference or email — is 409 `MONERIUM_B2B_CLIENT_CONFLICT`, checked at request time and again by the keeper before it pays for a deployment. The partner may register a rejected profile again, with the same or corrected data: the row is reset to `requested` (202). The registration reads the profile's state, never its kind, so a personal Monerium profile is accepted and mapped like a corporate one (an accepted scope decision, not a control). While `requested`, the snapshot carries `waitingReason`: `monerium_profile_pending` (created, incomplete, pending or review), `monerium_profile_not_visible` (Monerium answers 404), `deployment_pending`, `deployer_not_ready` (Vortex's deployer lacks the factory role or gas), `manager_inactive`, or `temporary_error` (RPC, Monerium or another transient failure). The keeper rejects a registration only for a definite reason: Monerium rejected or closed the profile; the factory refused the deployment's arguments (`InvalidConfigAddress`, `ZeroAddress`, `InvalidFeePolicy`); a client conflict; a mapping conflict that a retry cannot change; an operator mapped the profile by hand to a different destination; or an operator withdrew the registration. Every transient failure waits and is retried instead. Each cycle it evaluates the 20 least recently checked requested registrations (waiting ones never starve newer ones; one waiting for Monerium is asked again only after a minute) within a 15-second budget and sends at most one deployment (one key, implicit nonces), after the money steps and isolated in its own try/catch. It waits for the profile to be `approved`, then deploys the clone with the factory deployer key (a guardian-granted role, never the guardian key; its reach is bounded in Keeper invariant 1) at the CREATE2 salt `keccak256(abi.encode(moneriumProfileId, destination))`, which the factory binds to the whole initialization (destination, recovery address, fee policy), so nobody can occupy a client's predicted address with other settings, and a crash adopts the predicted clone instead of deploying twice. A deployment still in flight is waited for; one that reverted, or has no receipt after 10 minutes, is sent again. A clone found at the predicted address but out of the registry long after any deployment was revoked by the guardian; the registration is rejected, since the same destination would always land on it. An account an operator mapped by hand for the same profile is adopted when its destination matches the registration and it belongs to one of the registering manager's clients, and the registration is rejected otherwise. The keeper writes an outcome only while the row is still the one it loaded (status `requested`, same destination, reference and email) and holds a row lock while it maps, so an operator withdrawal or the partner's new attempt during a cycle wins and is never overwritten. Operators see every registration and the keeper's progress through `GET /v1/admin/monerium-b2b/registrations?status=requested|mapped|rejected` (ADMIN_SECRET; adds the registration id, contact email, manager profile, deployment hash and send time, and last check) and may withdraw one that is still `requested` with `POST /v1/admin/monerium-b2b/registrations/:registrationId/withdraw`: it becomes `rejected` with a Vortex-written reason and the partner registers the profile again with corrected data (409 `MONERIUM_B2B_REGISTRATION_NOT_WITHDRAWABLE` for any other status, 404 `MONERIUM_B2B_REGISTRATION_NOT_FOUND`). A clone already deployed for a withdrawn registration stays unused (no IBAN is linked to it) and the guardian may revoke it. Activation gates the money: only an `active`, non-dormant account swaps or forwards (`canConvert`), so a payment that reaches an account before the operator checked its destination waits on the clone (`DEPOSIT_UPDATED` and the deposits read show `waitingReason: account_not_active` for a minted or converting deposit on an account that cannot convert, cleared once it can) and the deadline refunds it. Accounts from registrations activate on their own only in the sandbox (`SANDBOX_ENABLED=true`, i.e. `DEPLOYMENT_ENV=sandbox`), once their IBAN is issued; in development, staging and production activation is the operator call. The gate is a keeper-side policy, not an on-chain guarantee: the deadline refund is automatic only with `MONERIUM_B2B_AUTO_RECOVERY=auto`, after `MONERIUM_B2B_RECOVERY_DEADLINE_MINUTES` (default 120; `alert` only logs REFUND DUE until an operator marks the deposit, `off` does nothing), and once a clone's batch has been open for `TRIGGER_DELAY` (24 h) `swap` and `forwardAll` are permissionless on an unpaused clone, so an early payment nobody marked for recovery can be converted and forwarded to the unchecked destination. The mapping then verifies that the forwarder's immutable `FACTORY()` equals `MONERIUM_B2B_FORWARDER_FACTORY_ADDRESS`, queries `isForwarder` on that configured factory (never a self-reported address; a clone the guardian revoked is refused), and reads back destination/targetPpm/floorPpm before persistence (the fee policy is validated as `0 <= targetPpm <= floorPpm <= 10000`, mirroring the contract; the clone has no fallback role and no destination setter). The managed child, customer entity, approved KYB mirror, and account then commit in one database transaction, so a late uniqueness conflict leaves no orphan identity records. Identical replay returns existing records; any divergence is 409, never an overwrite. A Monerium profile, forwarder, and managed profile can each back at most one account (migrations 069/071).
13. **Onboarding provider writes are exactly-once and provider reads are scoped** — the automated link (`POST /addresses`) and IBAN request (`POST /ibans`) run through the profile-scoped `financial_operations` ledger (flow `monerium-b2b-onboarding`), so crashes and retries never repeat a claimed provider call; interrupted calls reconcile by re-reading the linked addresses / issued IBANs. Every linked-address and IBAN selection requires the exact mapped profile, configured Monerium chain, and forwarder address; multiple exact IBAN matches are rejected rather than selected arbitrarily. Automation only touches accounts in `onboarding` status that have a managed-profile owner and no recorded IBAN (an account with its IBAN is fully linked and only awaits activation; the IBAN landing is logged). Activation precedes the penny test and is the operator's call except for sandbox registrations (invariant 12): only an `active` account converts.
14. **A recorded IBAN is never overwritten** — the `iban.updated` webhook (and the onboarding read) only fill a NULL `iban`; a delivery reporting a different IBAN for an account is logged at error level as a possible IBAN move (the S1 association-monitor alert condition), not applied.
15. **The read surface is effective-user scoped and accepts no selectors** — `GET /v1/monerium-b2b/account` and `GET /v1/monerium-b2b/deposits` resolve the account strictly from the acting profile (manager delegation via `X-Managed-Profile-Id` under the standard managed-profile authorization with EU corridor + business policy, or the child's own credential); no caller-supplied account, profile, or IBAN identifier is accepted, a foreign manager gets the uniform managed-profile 403, and R09 `unattr:` synthetic deposit rows are never returned. The one manager-level read, `GET /v1/monerium-b2b/accounts`, takes the manager's own credential only (the `X-Managed-Profile-Id` header is rejected with 400 and a child credential with 403), requires an active manager allowed the EU corridor and business customers, and lists only accounts whose managed profile is an active child of that manager; its optional `moneriumProfileId` filter narrows within that set and never widens it (`monerium-b2b-account-read.integration.test.ts`). `GET /v1/monerium-b2b/registrations` has the same credential rules and lists only the caller's own registrations, with `waitingReason` while one is `requested`. `POST /v1/monerium-b2b/accounts` has the same credential rules and is further limited to the one bound partner manager and refuses an admin impersonation token (reads stay allowed); it takes no KYB data (invariant 11) and stores only the profile ID, destination, client reference and contact email (`monerium-b2b-registration.integration.test.ts`).
16. **Manager deposit events are final, chain-backed, and manager-only** — `DEPOSIT_RECEIVED` requires the real chain id, transaction hash, log index, and block number, so a provider order alone cannot claim that funds landed. `DEPOSIT_RECEIVED` fires for any state past the mint (the keeper may already have started converting within the cycle). `DEPOSIT_CONVERTED` fires once only after the deposit is `forwarded` and its confirmed `forward` execution is `NOTIFY_CONFIRMATION_DEPTH` blocks deep; its `conversions[]` lists the deposit's confirmed chunk swaps (EURe in, net USDC, reference rate, fee and subsidy per chunk in the `execution` block), `forwardTxHash` is the single transfer to the destination and payload `usdcNetRaw` is the amount that transfer carried. `DEPOSIT_RETURNED` fires once when a deposit is `refunded`, carrying the refunded EUR amount, the payer's IBAN masked to its first and last four characters (the full IBAN never leaves the backend), Monerium's redeem order id and the `recover` transaction. Per-deposit markers prevent replay to late subscribers. `DEPOSIT_UPDATED` and `ACCOUNT_UPDATED` send the full deposit or account snapshot (the read-surface shape) whenever its SHA-256 differs from the last one sent, with an `eventId` that embeds the hash so outbox dedup absorbs a crash between enqueue and marker; a `forwarded` deposit is reported only under the same confirmation-depth gate as `DEPOSIT_CONVERTED`, and snapshots carry the payer IBAN only masked. Deliveries go only to the controlling manager's webhooks through the durable outbox; `unattr:` rows never emit (`manager-events.test.ts`).
17. **Account lifecycle transitions are explicit** — operators list accounts, optionally by status, with their partner manager through `GET /v1/admin/monerium-b2b/accounts` (ADMIN_SECRET). `onboarding → {active, suspended}`, `active → {suspended, closed}`, and `suspended → {active, closed}` are the only state changes; `closed` is terminal. Suspending an onboarding account records a failed destination check: nothing converts, recoveries still run, and onboarding automation no longer touches it, so it requires the issued IBAN too (409 otherwise; without it the account could never be activated). Activation requires the issued IBAN (409 otherwise) and sets `activated_at`, the dormancy anchor (Keeper invariant 6); every status change is logged with the account, from and to status, destination and forwarder (ADMIN_SECRET carries no operator identity). Repeating the current status is idempotent. The admin controller returns 409 for every invalid edge, including reopening a closed account or moving an active account back to onboarding (`moneriumB2b.controller.test.ts`).

## Keeper

The keeper loop (`workers/monerium-b2b.worker.ts`, every `MONERIUM_B2B_KEEPER_CYCLE_SECONDS`, default 20: webhook inbox → onboarding → mint watcher → per-account conversion executor → dormancy gate → refund deadlines and orchestrator → partner registrations → manager events and monitoring) holds signing keys and submits transactions; the registration step runs after the money steps and isolated, so a slow Monerium or RPC read never holds back a conversion or refund. Its invariants:

1. **Three-way key separation, bounded fund movement** — the keeper key (`MONERIUM_B2B_KEEPER_PRIVATE_KEY`, submits `poke()`, `applyFeePolicy()`, `swap()`, `forward()` and `recover()`), the guardian key (`MONERIUM_B2B_GUARDIAN_PRIVATE_KEY`, dormancy pause only), and the attestor key (address linking only) are three distinct keys. None of them can redirect funds: `swap` only executes a factory-whitelisted, oracle-floored swap whose USDC stays on the clone, priced against a keeper-supplied reference the contract bounds to `MAX_REFERENCE_DEVIATION_BPS` around Chainlink (invariant 7); `forward` only ever pays the clone's own `destination`; `recover` only ever pays the clone's `recoveryAddress`, the client's refund wallet fixed at deployment with no setter, and only once the clone's batch marker has been open for `RECOVERY_DELAY` (the contract, not the keeper, enforces the promised window); `setGuardianPaused` is protective-only by contract invariant (it blocks swaps and forwards, never a recovery); the attestor signs the fixed link statement. Besides the guardian, an address the guardian registers on the factory as a deployer (`setDeployer`) may call `deployForwarder` and no other factory or clone function, so deploying needs no guardian signature; the backend's deployer key (`MONERIUM_B2B_DEPLOYER_PRIVATE_KEY`, distinct from the other keys) holds that role for partner registrations (invariant 12). The role is not harmless, though: every clone a deployer deploys is registered (`isForwarder`), the trust anchor of the subsidy vault's `pay` and of the backend's mapping check, and a deployer may pick any destination and recovery address. A leaked deployer key can therefore create registered clones of its own, fund them itself and draw vault subsidies within the vault's per-swap cap and daily budget; it can touch no existing clone's funds or configuration. The guardian bounds it: `setDeployer(address, false)` stops new deployments but does not unregister clones already deployed, and `revokeForwarder(clone)` (guardian-only, one-way, emits `ForwarderRevoked`, reverts `UnknownForwarder` for an unregistered address) removes one from the registry, after which the vault refuses its subsidy calls, so a swap that needs a subsidy reverts, and the backend refuses to map it (the config reconciliation, R07, reports the revoked clone of an onboarding or active account as an error); its forward and recover paths and its funds are untouched. The factory binds each clone's CREATE2 address to its whole initialization, `keccak256(abi.encode(destination, recoveryAddress, targetPpm, floorPpm, salt))`, so `predictAddress` takes all five arguments (manual deploys too) and a deployer cannot squat an address predicted for other settings. Deployers survive a guardian transfer like keepers: a new guardian must review the `DeployerSet` events and reset them. The role takes the guardian key out of deployment only, not off the server: the dormancy pause (invariant 6) still signs with it. A clone still passes the account mapping's on-chain verification (trusted factory, `isForwarder`, destination, fee policy, derived refund wallet) before it is used. Vortex therefore holds a client's funds only on the refund path, only in that client's own refund wallet, and only for a payment the promised window was missed on (adr-0005, amendments 2026-09-17 and 2026-10-01). All keys are env-only and never logged.
2. **Private orderflow for keeper writes** — keeper/guardian transactions are submitted through a dedicated transport (`MONERIUM_B2B_PRIVATE_RPC_URL`, e.g. `https://rpc.flashbots.net`), separate from the read/receipt client (`MONERIUM_B2B_RPC_URL`). If the private endpoint is unset the keeper falls back to the public RPC and logs a warning — acceptable on sandbox/testnet, an operational finding on mainnet. Known limit: the keeper's nonce reads use the public read RPC (the value path's explicit nonce, the re-send's nothing-pending check), which cannot see a keeper transaction still unmined in the private relay (a `poke` or `applyFeePolicy` sent with an implicit nonce), so a later send can take the same nonce; only one transaction per nonce is mined, and a losing value-moving row fails closed through the exact-match recovery (invariant 3) and retries after the backoff, so the cost is delay, never a double send.
3. **Execution record and exact recovery before resend** — the pending execution row is committed before broadcast. A nonce-less row is a five-minute pre-send reservation; expiry and swap-nonce persistence are competing compare-and-set updates, so an expired owner cannot later broadcast. Any required, non-value-moving `poke()` is sent first. Only after it succeeds are the exact swap nonce and pre-broadcast chain head persisted immediately before `swapAndForward()`, then the hash immediately after broadcast. A receipt finalizes normally. A missing receipt never becomes failure on elapsed time. While the latest confirmed nonce has not passed the persisted nonce, the row stays pending even if the public mempool cannot see it. A reserved nonce that is never mined (the process died before broadcasting, the send threw, or a private relay dropped the transaction) would hold the keeper's nonce, the account and its refund path forever, so once the row has been idle for the five-minute pre-send deadline (`updated_at`, its last write: the reservation or the hash write) and the nonce is not yet mined with nothing pending at the keeper's next nonce, the keeper (first filling any gap below the row's nonce, left by a dropped `poke()`, with zero-value self-transfers; the gap is not re-poked, because the re-sent `swap` or `forward` arms an unarmed marker itself and, after a no-op, the next cycle pokes, so a dropped poke delays the recovery clock by about the five-minute idle deadline) re-sends the row's exact `expectedCalldata` at that same nonce, under the keeper send lock (taken after the forwarder lock, never the reverse) so a live owner still about to send is waited for, and persists the new hash. One transaction per nonce can be mined and either copy is the expected call, so the exact-match recovery below adopts whichever lands. If the call no longer executes (gas estimation reverts, e.g. a stale persisted reference; a non-revert error such as an RPC timeout or an unfunded keeper only leaves the row pending), a revert-protecting private relay would never mine it, so the keeper consumes the nonce with a zero-value self-transfer instead; a swap or forward of an account that cannot convert (not activated, suspended, dormant or closed: `canConvert`) is treated the same way, so neither the activation gate nor an operator's suspension is ever overridden by a re-send, while a `recover` (the refund path) is exempt from that status gate and only consumed by the no-op if its own estimate reverts; the next cycle sees the nonce consumed without the expected transaction, fails the row, and the retry backoff and a fresh plan apply. The retry backoff (1 min, doubling per failed row since the account's last confirmed execution, at most 60 min) holds a swap or forward back on failures of any kind, but a planned `recover` only on failed recovers, so failing swaps never delay a refund past its on-chain eligibility. A failed re-send leaves the row pending. Once consumed, recovery scans sequential, bounded 2,000-block pages from the persisted head and adopts only one unclaimed transaction whose sender is the keeper, nonce is exact, target is this forwarder, calldata is exactly the row's kind rebuilt from what was persisted before broadcast (`expectedCalldata`: `swap(referenceRate, routeIndex, amountIn)`, `forward(amount)` or `recover(eureAmount, usdcAmount)`), and receipt emits that kind's event (`SwapExecuted`, `Forwarded`, `Recovered`) from the forwarder. A confirmed `forward` or `recover` also requires the event's amounts to equal the planned ones, else the row fails. Incomplete/ambiguous scans remain pending; only a complete scan with no exact match proves failure. This fail-closed posture can require manual reconciliation, but cannot double-convert. Keeper nonce derivation/broadcasts serialize across processes via a send advisory lock.
4. **Advisory-lock serialization** — all keeper database mutations (mint recording, action planning, execution slot check/creation with the deposit's status transition, finalization, the operator's recovery marking) run inside the shared per-forwarder `pg_advisory_xact_lock` (`withForwarderLock`), the same lock the webhook deposit processor uses. Double-send is prevented by the "any pending execution → skip" check under that lock; the chain send/wait itself intentionally runs outside a database transaction so the pending record cannot be rolled back by a crash. The one exception is the send-only re-send of an idle, never-mined reserved nonce (invariant 3): it runs under the forwarder lock (keeper lock inside it), only after the idle deadline, and a lost hash write is recovered by the exact scan.
5. **One deposit at a time, chunked, forwarded whole (1 deposit : N executions)** — the keeper serves the oldest chain-indexed, provider-attributed deposit that is still settling: it swaps one chunk of it per cycle with an explicit `amountIn` (`planChunk`: at most `perSwapCap`, never leaving a sub-minimum dust remainder when the last two chunks can share it; a remainder below `minSwapAmount` waits for the refund path with `waitingReason` `below_minimum` and is passed over, so it never holds back a younger deposit; the trade-off is ordering: a younger deposit forwards before the older passed-over one is refunded, and each `forward` resyncs the batch marker (`_syncBatch(true)`); on a clone left with less than `MIN_SWAP_FLOOR` EURe and no USDC the marker switches off or never arms, so such a payment is refunded only after the operator's top-up (Monitoring invariant 3), later than the promised window; while the clone stays funded (a passed-over remainder at or above `MIN_SWAP_FLOOR`, possible only with `minSwapAmount` above the floor, or a chunk-swapped remainder whose USDC is still on the clone) each younger `forward` re-times the marker, so the passed-over deposit is recover-eligible only after a forward-free `RECOVERY_DELAY`, and Monitoring invariant 3 reports it as REFUND OVERDUE), every `swap` execution row carries the deposit it serves, and once the chunks' EURe sum to the deposit's amount one `forward` execution pushes the sum of their nets to the destination. Deposits never share a swap, so no pro-rata attribution exists; `unattr:` rows are never converted and never surface as customer claims. Only chain-indexed, provider-attributed deposits make an account a conversion candidate (an `unattr:` row only for the cycle its mint lands in; the mint watcher scans 12-deep blocks; identity `(chain_id, tx_hash, log_index)`), and a raw forwarder balance never bypasses the watcher. Execution net is `usdcOut - fee + subsidy` from `SwapExecuted` (the subsidy lands on the clone and is forwarded with the payment); unsolicited USDC on the clone is never credited to a deposit and leaves only through the keeper's `forwardAll`. A hash match with a conflicting amount is refused: the chain log is recorded separately as unattributed, the provider row gets no chain identity, and an error alert fires.
6. **Dormancy pause is protective-only (R05)** — after 60 days (registry P5) without a confirmed conversion, counted from the later of the last confirmed conversion and the activation (else the account's creation, so an account activated long after it was mapped is not paused at once), the gate calls per-clone `setGuardianPaused(true)` with the guardian key (log-only when the key is unset) and records `dormant_since`; account status stays `active`. The pause can never move funds and never blocks a recovery (contract invariant); un-pause is a manual guardian operation (registry B5). The batch marker still arms for dormant and suspended accounts (`poke()` is pause-immune) and the keeper still recovers their marked deposits: the refund path exists precisely for payments nobody is converting any more.
8. **The refund runs one payment at a time per client on a dedicated wallet, and only Vortex money moves off chain** — `recovery.ts` (`MONERIUM_B2B_AUTO_RECOVERY=auto`; `alert` reports, `off` is manual) opens a `monerium_recoveries` row only for a confirmed `recover` execution of a `recovering` deposit, and only for a client with no open row: at most one open row per client, each stepped at most once per keeper cycle; the keeper refuses a second `recover` for an account while one of its refunds is in flight (`activeRecoveryExists(accountId)`), and a refund parked in `recovery_failed` blocks only its own client's later refunds. Clients' refunds run side by side, but the shared EURe float wallet (implicit nonces over an RPC with no coherent pending pool) is serialized: per cycle, steps that cannot send from it run concurrently (one client's slow receipt wait does not hold the others' steps within the cycle, but the cycle lasts until the slowest wait ends: a cycle can last several minutes, since each receipt wait times out after 3 minutes and a float step can wait on more than one; other clients advance one step per cycle; and because clients share the one float wallet, a slow float transfer can delay another client's float step), alongside at most one step that sends from it (`sendEure`, `sendReverseSwap`, including the refund wallet's gas top-up), and none while a `topping_up` recovery still waits on its float transfer's receipt (a parked one is never stepped and does not hold the gate; so a second EURe top-up cannot reuse the first one's pending nonce or read the float balance before its debit). The gate covers top-up transfers whose hash is recorded; a float gas top-up whose receipt wait times out inside a step is retried from balances on a later cycle, and on an RPC without a coherent pending pool it can still collide with another client's float send in the meantime, which costs a retry, not funds; likewise an operator who parks a `topping_up` refund by hand while its float transfer is still pending releases the gate, and that transfer can still mine under the next client's float send (the runbook says to check the float's pending nonce, or cancel or replace the transfer, before parking); the float steps start no new step after 90 s. The refund runs on the client's refund wallet, an EOA whose key is derived from `MONERIUM_B2B_REFUND_SEED` and the client's Monerium profile ID (`refund-wallet.ts`); it is linked to the client's profile at onboarding, so the redeem pays out of the client's own IBAN, and no wallet ever holds two clients' funds. Every step re-derives its remaining work from that wallet's live balances, so a transaction whose hash was lost is never repeated: a landed reverse swap shows as USDC gone, a landed top-up as the need reaching zero. The reverse swap runs on the reversed whitelisted route with a minimum output of the Chainlink value less `SLIPPAGE_BPS`; the float pays only the difference to the exact issue amount and receives any surplus. The redeem order is placed from the refund wallet with the issue order's amount, the payer's IBAN and name captured from the issue order's counterpart, and a memo `vortex-refund:<depositId>` that is checked at Monerium before every placement (exactly-once). Five failed attempts during one refund (counted across its steps, since a sent step can still revert) park the deposit as `recovery_failed` with the phase preserved for the operator's retry; amounts of EUR 15,000 and above, a missing payer, or a rejected order park it for the operator to refund by hand under the same memo and close the deposit as `refunded`, after which the orchestrator closes the recovery without placing an order. A rejected order's id is dropped from the recovery (kept only in its error), so no partner event names an order that paid nothing. The recovery row is marked `redeemed`, and `error` recorded on a park, only after the deposit transition succeeded, so a refused or failed transition keeps the recovery open and is retried on the next cycle. The refund seed and the float key are env-only and never logged; the seed is required whenever the module is enabled (onboarding links the derived wallet), the float key in `auto` mode, and the derived wallet must equal the clone's `recoveryAddress` before any send. Account mapping refuses a clone whose `recoveryAddress` is not the client's derived wallet, and the admin refund-address endpoint returns only the address. Before the refund wallet sends its own transactions, the float tops its ETH up to twice their cost at the current gas price (balance-derived, so a repeat sends nothing). `payer_iban`/`payer_name` are financial-record PII kept with the deposit row (the raw webhook is pruned after 30 days); they are never returned by the read API.
7. **Swaps are reference-priced, subsidy-bounded, and deferred rather than forced** (adr-0005 amendment 2026-09-15; behaviour in architecture-monerium-b2b-onramp.md) — before every swap the keeper reads the Coinbase Exchange EURC-USDC top of book and takes the bid/ask midpoint (`reference-rate.ts`; a spread above 50 bps or an inverted book defers, so a thin market never sets the reference), records price, source and time on the execution row before broadcast, and passes the rate into `swap`; the contract rejects a reference outside `MAX_REFERENCE_DEVIATION_BPS` of Chainlink, and a permissionless caller's value is ignored in favour of Chainlink with no subsidy. The keeper also passes `maxSubsidy`, its subsidy tier for the time the chunk has waited (`MONERIUM_B2B_SUBSIDY_LADDER`, `maxSubsidyBpsFor`, per-chunk clock from the mint or the previous chunk's confirmation), persisted on the row before broadcast and part of the calldata-exact recovery identity; the contract refuses a top-up above it, so the tier binds at execution whatever the fill did after the quote. The ladder is a Vortex spending policy (the client's floor never moves), bounded on chain by the vault's cap and budget. On chain the Chainlink floor `_floorOut` (`SLIPPAGE_BPS`) bounds both bands from below (amendment 2026-09-18): the fee is the surplus above `max(reference x (1 - targetPpm), oracleFloor)` capped at `MAX_FEE_PPM`, the subsidy is the shortfall below `max(reference x (1 - floorPpm), oracleFloor)`, and `SLIPPAGE_BPS` is still enforced on the client's net after both, so a reference under a stale Chainlink round costs Vortex fee and subsidy (within the tier and the vault) rather than the client, while a depeg beyond what the tier and the vault cover reverts. The subsidy comes from one shared `VortexSubsidyVault` that pays only when called by a factory-registered clone, only within a per-swap cap (ppm of the reference value) and a UTC-daily budget, can be paused, and withdraws only to the treasury; a vault that cannot cover reverts the whole swap, and the clone counts a subsidy only after verifying that exactly the shortfall landed on the clone itself (it is forwarded with the payment), so a misconfigured or hostile guardian-set vault cannot make a below-floor fill pass (`test_swap_subsidyNotDelivered_revertsTheWholeSwap`). The keeper mirrors this settlement off-chain (`projectSwap`, unit-tested against the Foundry numbers) and defers — no execution row, funds wait, marker armed — when the reference is unavailable or out of band, no route quotes, the projected subsidy exceeds the cap, the remaining budget or the balance, or the projected net would breach the floor. Routes are keeper-picked by quote among factory-validated entries (EURe, EURC and USDC only, the four Uniswap tiers, at most two hops, the immutable router); a poor pick costs Vortex subsidy or fee, never the client. Accepted consequence: the subsidy widens the sandwich-exploitable band from `SLIPPAGE_BPS` to floor plus cap, paid by the vault — private orderflow (invariant 2) and a modest cap are the mitigation, and the permissionless path keeps the plain floor. A guardian fee increase (registry P11) takes effect only through the permissionless `applyFeePolicy()` once `FEE_INCREASE_TIMELOCK` (24 h) has elapsed: in each account cycle, before pricing, the keeper sends it when the latest block's timestamp has reached `pendingFeePolicyEffectiveAt` and waits for the receipt, so the cycle's swap is projected under the policy it settles at; a timed-out apply is not re-sent and stacked every cycle: the keeper remembers each forwarder's last apply in process memory and sends nothing while that apply has no receipt and is younger than 15 minutes (longer than a private relay keeps a transaction; keeper writes go through the private transport on mainnet, which the public nonce counts never show), nor while the public pool holds any keeper transaction, of any account (latest and pending nonce differ), and logs each skip reason once; a restart forgets the remembered apply, and another keeper process on the same database never knew it, so either may send one duplicate, which reverts `NoPendingFeePolicy` or is dropped; a failed read of the pending policy, a revert (already applied by someone else, clock skew) or a timeout is logged and the cycle goes on, because the contract always settles under its currently applied policy. The account row follows through the config reconciliation (Monitoring invariant 5). The keeper only runs for accounts with a settling deposit, so a due increase on an idle clone is applied before that clone's next swap, not at the deadline.

## Monitoring

The monitoring pass (`monerium-b2b/monitoring.ts`, run from the worker, rate-limited to one pass per 30 minutes) is detection-only; its invariants:

1. **No keys, no transactions** — monitors read chain state (`MONERIUM_B2B_RPC_URL`) and the Monerium API only; they never hold private keys and never broadcast. The only database mutation is the R07 reconciliation in (4). Alerts go through the standard logger (`error` = incident trigger per the B2B operations runbook).
2. **Executable-depth check (PRD §7.4)** — QuoterV2 static quotes on every enabled factory route at `minSwapAmount` and `perSwapCap` sizes, compared against Chainlink EUR/USD (`computeQuoteImpactBps`, unit-tested against the T6 baseline); the best route decides. Settlement enforces `SLIPPAGE_BPS` on the client's net, so a raw impact above it means every keeper swap of that size draws a vault subsidy (deferring past the per-swap cap) and the permissionless path would revert; at `minSwapAmount` size that logs the error-level DEPTH BELOW FLOOR line, at `perSwapCap` size a warning (`classifyExecutableDepth`). The keeper's own `projectSwap` deferral remains the authoritative gate. Both this check and the keeper's route quoting use the QuoterV2 pinned per chain id (`quoterV2ForChainId`: Ethereum mainnet and the Sepolia sandbox, each on the chain's own Uniswap v3 deployment), so the sandbox projects and defers like production; on a chain without a pinned quoter the check is skipped and the keeper takes the first enabled route unprojected, leaving the contract's checks as the only gate. On the sandbox the DEPTH BELOW FLOOR line therefore also fires whenever the Sepolia pool drifts from the Sepolia oracle; there it is a pool-calibration signal, not a production incident, so off mainnet (chain id other than 1) it is logged as a warning naming the chain with a hint to re-centre the sandbox pool, keeping invariant 1's rule that an error is an incident trigger.
3. **Stranded-balance monitor** — forwarders holding ≥ `MIN_SWAP_FLOOR` EURe or any USDC whose on-chain batch marker has been open longer than `RECOVERY_DELAY` (2 h, registry P3) warn — the promised window was missed and the deposit should be forwarded or recovering; past `TRIGGER_DELAY` they error (the permissionless swap/forward path is then live — a keeper-outage signal, not a fund-risk signal). A clone below that threshold arms no batch, so `recover` reverts: a deposit marked `recovering` there without a pending or confirmed `recover`, with no confirmed swap, raises the error-level REFUND NEEDS OPERATOR line. Its remedy is a top-up, never a hand refund: the line names the clone, its EURe balance and the exact amount, `MIN_SWAP_FLOOR - balance + 1 wei` (one wei more when that is a whole number of cents; decimal and raw) of the EURe token, which the operator sends exactly as printed to the clone from any wallet (e.g. the float). The permissionless `poke()` (or the keeper's) then arms the marker, and after `RECOVERY_DELAY` the keeper's normal `recover(remaining EURe, 0)` and refund pipeline refund the payer's own EURe, under the same one-refund-per-client gate (`activeRecoveryExists`) and with the full record (recover transaction, redeem order, `refundedAt`). That refund pipeline runs only with `MONERIUM_B2B_AUTO_RECOVERY=auto`: in `alert` or `off` the keeper's `recover` still moves the payment to the client's refund wallet, and the line says so and points the operator to the manual redeem from that wallet instead of forbidding a hand refund. The top-up stays on the clone, below the floor, as Vortex EURe, so `recover`'s `_syncBatch(true)` switches the marker off again. The top-up amount is never a whole number of cents (orders and the floor are), so the mint watcher can never match it to a Monerium order by amount, even when an earlier top-up's odd wei is still on the clone; it is recorded as one `unattr:` Minted row (one warn) that the keeper never converts. Leftover top-ups stay below EUR 1 per clone; a later sub-floor payment that reaches the floor with them arms the marker and is refunded without an operator step. The line fires only while the clone holds at least all the EURe the ledger places there: every minted (including `unattr:` top-ups), converting, recovering or refunded deposit's unswapped rest without a confirmed `recover` (a legacy hand refund left its EURe on the clone). A landed top-up lifts the clone to the floor, so the check stays quiet until the keeper's `recover` took the payer's EURe. While any `recover` of the account is still pending, the account is skipped for that pass: a mined `recover` whose row is not yet confirmed would make the ledger count EURe that already left, and turn a sibling's alert into a false "reconcile". On a clone at or above the floor (or holding USDC), a deposit marked `recovering` with no pending or confirmed `recover` whose `refundStartedAt` is older than `RECOVERY_DELAY` plus one hour (the refund monitor's linger margin) raises REFUND OVERDUE, a warning, and an error once it is older than `TRIGGER_DELAY`: younger forwards may keep re-timing the marker so it never becomes recover-eligible, or another refund of the client may be stuck. After a late operator top-up it can show until the keeper's `recover` lands. A swapped deposit, or any shortfall, means part or all of the funds left by an unrecorded path (e.g. the permissionless swap/`forwardAll`), so it only warns "part or all of their funds left the clone: reconcile before refunding; do not refund and do not top up the clone".
4. **Association monitor (S1 detective control)** — per active account, re-reads linked addresses and IBANs scoped to the exact mapped profile and configured chain, then error-alerts on ANY divergence from the DB record (forwarder unlinked, extra address linked, IBAN moved or unrecorded — `diffAssociation`, unit-tested). The only address besides the forwarder that is expected on the profile is the client's own derived refund wallet (`refundAccountFor(profileId)`, linked at onboarding); any other address still alerts, and with no refund seed configured no wallet is excused. This is the detective control for the S1 risk (Vortex-held whitelabel credentials can move associations at Monerium): changes cannot be prevented client-side, only detected.
5. **Config reconciliation (R07)** — first requires the clone's immutable `FACTORY()` to equal the configured trusted factory, then reads `implementation()` and `isForwarder()` only from that trusted address. A mismatch is an error and no mutable fields are reconciled. For trusted clones, timelocked fee-policy changes are authorized transitions reconciled with a version bump; a destination change (the clone has no setter), proxy bytecode or registration drift is an incident. The standalone manifest verifier remains consistency evidence, not the trust root.
6. **Subsidy-vault monitor** — reads the factory's vault balance, daily budget, spend and pause state (`classifyVaultRunway`, unit-tested): paused or empty is an error (every below-floor swap defers), less than one day of budget or an exhausted day is a warning; a missing vault warns once per pass.
8. **Refund monitor** — with automated refunds configured, every open recovery is classified on its own: it warns after an hour and errors after four or on a failed step, so each parked refund alerts (`classifyRefundQueue`, unit-tested); the float's EURe balance errors when empty and warns below 1,000 EURe; the float's ETH, which pays for its own sends and the refund wallets' gas, warns below 0.05 ETH and errors once it cannot pay for one 21k-gas transfer at the current gas price.
7. **Reference-venue monitor** — probes the status of the Coinbase Exchange product the reference midpoint reads (`fetchCoinbaseProductStatus`, `classifyReferenceVenue`, unit-tested); anything but an online product with trading enabled is an error, because a delisted product keeps answering the candles endpoint with stale data and every keeper swap would defer silently (EURC-USD did exactly that after its 2024-08-29 delisting).

## Threat Vectors & Mitigations

| Threat | Attack Scenario | Mitigation |
|---|---|---|
| **Webhook spoofing** | Attacker posts fabricated order events to `/v1/monerium-b2b/webhook` to invent or advance deposits | Monerium v1 HMAC over signed id + timestamp + raw bytes, constant-time compare; 401 before persistence; enabled startup refuses a missing secret. The HMAC holds only against parties without the secret (see **Partner-held white-label credentials**) |
| **Cross-account/provider poisoning** | A valid provider event names another chain/profile, or a claimed mint hash carries a different amount | Strict wire/chain/profile/currency checks; hash+amount must both match before chain identity or `DEPOSIT_RECEIVED`; conflicting chain logs are isolated as `unattr:` |
| **Lost or replaced keeper transaction** | A slow/hidden transaction is declared stale and a second swap sends the same funds | Compare-and-set pre-send reservation; no time-based failure after nonce persistence; fail-closed nonce state; an idle, never-mined reservation is re-sent identically at its own nonce, or that nonce is consumed by a no-op when the call no longer executes, never reused for another call; bounded complete persisted-block scan plus exact sender/nonce/target/calldata/event identity before adopt/fail |
| **Executor outruns mint indexing** | A live balance is swapped before its mint identity is settled, leaving a swap with no deposit to belong to | Conversion candidates require chain-indexed deposits; every swap is bound to one deposit before it is sent, with an explicit `amountIn` |
| **Unsolicited USDC inflates deposit reporting** | USDC that arrived outside a swap is credited to a deposit | Execution net is `SwapExecuted.usdcOut - fee + subsidy`; a deposit's forward moves exactly the sum of its chunks' nets; unsolicited USDC leaves only through the keeper's `forwardAll` and is never reported as a conversion |
| **Premature or misdirected recovery** | A compromised keeper moves a fresh payment off the clone, or to a wallet of its choosing | `recover` pays only the clone's fixed `recoveryAddress` (the client's derived refund wallet, verified at mapping), only after the clone's batch has been open for `RECOVERY_DELAY`, with explicit amounts bounded by the balances; a deposit enters the refund path only through the admin endpoint (operator) or, once automated, the deadline; the invariant suite proves no early recovery and no other exit |
| **Refund wallet or seed compromise** | A client's refund wallet is drained before the refund, or the seed leaks and exposes every client's wallet | Funds sit on a refund wallet during that client's recovery, or after a payer memo-routes a payment to it until an operator refunds it (runbook §2.7, "Memo-routed payment"); each wallet holds only its own client's funds; one refund per client at a time; the seed is env-only and never logged; rotating it means new clones for every client (runbook §5 and §6) |
| **Reverse-swap sandwich or thin reverse route** | A searcher moves the pool while the refund's USDC is swapped back, or the pool is too thin | Minimum output at the Chainlink value less `SLIPPAGE_BPS`; private orderflow; a rejected or reverted swap retries on the next keeper cycles and parks the refund for the operator after five failed attempts; the float, not the payer, absorbs slippage |
| **Double refund** | A crash between the redeem POST and its persistence places the order twice, or a lost top-up hash sends the float twice | Memo-keyed lookup at Monerium before every placement; balance-derived need (a landed top-up makes the need zero); one open recovery per client on an otherwise empty wallet; float sends serialized across clients |
| **Refund to the wrong account** | A tampered or missing counterpart sends the EUR elsewhere | The target is the issue order's own counterpart, recorded once and never overwritten by a later delivery; a deposit without it never refunds automatically (`recovery_failed`, runbook) |
| **Manipulated reference rate** | A compromised keeper (or Coinbase response) supplies a reference that inflates the fee or triggers a subsidy | Contract band check against Chainlink; fee capped at `MAX_FEE_PPM`; subsidy bounded by the vault's per-swap cap and daily budget; the floor on the client's net; a permissionless caller's reference argument is ignored in favour of Chainlink |
| **Subsidy-widened sandwich** | A searcher moves the pool so the fill lands just above floor minus cap and the vault pays the difference | Private orderflow for keeper swaps; modest per-swap cap and daily budget; the vault, not the client, absorbs the loss; no subsidy on the permissionless path |
| **Subsidy vault drain** | A contract or key tries to pull vault USDC | `pay` accepts only factory-registered clones and pays only the calling clone, within cap and budget; the clone verifies the exact delivery; withdrawals go to the immutable treasury only; guardian setters bound Vortex's own money, never client funds |
| **Untrusted forwarder factory** | Admin-secret holder submits a contract whose self-reported factory blesses it and redirects mints | Configured factory is the trust root for provisioning, execution, and monitoring; local provisioning is atomic |
| **Deployer key leak** | Attacker obtains `MONERIUM_B2B_DEPLOYER_PRIVATE_KEY` and deploys registered clones with its own destination and recovery address, funds them itself and draws vault subsidies, or deploys at an address predicted for a client | The role can only deploy; clones are registered, so exposure is bounded by the vault's per-swap cap and daily budget, and no existing clone's funds or configuration are reachable; the CREATE2 address commits to the whole initialization, so a client's predicted address cannot be occupied with other settings; guardian `setDeployer(address, false)` stops deployments and `revokeForwarder(clone)` removes a rogue clone (vault refuses it, mapping refuses it); the key holds gas only and differs from every other B2B key |
| **Registration plants a payout destination** | A stolen partner manager key, or an operator's impersonation token acting as the partner manager, registers a client profile with a wallet of the attacker's choosing | Only the one bound manager, never an impersonation token (403); only a profile the partner's app can read and Monerium has not rejected or closed; create-only per profile, so a different destination is 409 and a rejected profile is registered again only by the partner; the clone is verified on chain before mapping; the account converts only once an operator activates it (production, staging, development); `ACCOUNT_UPDATED` echoes the destination; an operator can withdraw a requested registration |
| **Money reaches an account whose destination nobody checked** | A client pays the IBAN before the operator activated the account, with a typo in the partner-supplied destination | `canConvert` holds the deposit on the clone and shows `account_not_active`; the refund runs automatically only with `MONERIUM_B2B_AUTO_RECOVERY=auto`; with `alert` or `off` an operator must mark the deposit before the clone's `TRIGGER_DELAY` (24 h), after which `swap` and `forwardAll` are permissionless on an unpaused clone (keeper-side policy, not an on-chain guarantee) |
| **Webhook replay / duplicate delivery** | A captured valid delivery is replayed to double-count a deposit | Durable inbox dedup on unique `event_id` (`ON CONFLICT DO NOTHING`); forward-only transitions make a replayed older state a no-op |
| **Out-of-order events regress state** | A delayed `pending` event arrives after `minted` | Forward-only transition lattice; regressions logged and dropped |
| **Attestor key leak** | Attacker obtains `MONERIUM_B2B_ATTESTOR_PRIVATE_KEY` | Blast radius is bounded by design: the key can only produce link attestations for the fixed message, never move funds (contract-side invariant); rotate key + re-deploy forwarders with new ATTESTOR immutable |
| **Attestor signing oracle abuse** | Backend is tricked into signing an arbitrary hash with the attestor key | `signLinkAttestation` derives the hash internally from the fixed LINK_MESSAGE and the forwarder address parameter; no caller-supplied hash is ever signed |
| **Concurrent processors corrupt attribution** | Two instances process events for one account simultaneously | Transaction-scoped Postgres advisory lock per forwarder address serializes all per-account writes |
| **Lost webhook between receipt and processing** | Process crashes after 200 but before the deposit write | Insert-before-200 durable inbox; unprocessed rows are retried on the next run |
| **Poison inbox row blocks processing** | A malformed payload throws forever | Non-order/unrecognized payloads are marked processed and skipped; genuine failures are logged per-row and do not block other rows |
| **API credential compromise** | White-label client id/secret leak, from Vortex's env or from the partner, who holds the same credentials | Env-only storage at Vortex; the whitelabel credential set (`MONERIUM_WHITELABEL_*`) is distinct from the legacy OAuth auth-code client (`MONERIUM_CLIENT_ID`); rotate in the partner's app at Monerium, coordinated with the partner; the S1 association monitor detects unauthorized use |
| **Partner-held white-label credentials** | The partner owns the white-label app and holds its credentials with the same control-plane power as Vortex (ADR-0005 S1): it can re-link addresses, move IBANs and close profiles. Any holder can also list the app's webhook subscriptions, Vortex's included. If that listing returns the subscription secret (Monerium's guide says so; its response schema has no secret field), the holder can sign order events that pass the HMAC, and a forged delivery that lands before Monerium's sets the deposit's refund target, which is recorded from the first delivery and never overwritten | Accepted trust in the partner (ADR-0005 S1): the association monitor alerts on a re-linked address or a moved IBAN, and any such change is an incident (runbook §2.5); forged events can create or advance deposit records but cannot make the keeper convert or forward anything that did not mint to the clone, because conversion needs the chain-indexed mint with a matching hash and amount. **Open:** confirm in the sandbox whether the subscription listing returns secrets, and read the payer IBAN and name back from Monerium's API instead of relying on the webhook alone (rollout ledger, "Monerium read-back") |
| **Provider unavailability** | Monerium API down | Client calls have explicit timeouts and surface 502; webhook inbox is unaffected (processing is local) |
